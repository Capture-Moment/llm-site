# llm-site — AI Backend & Knowledge Base

AI backend of the **CaptureMoment** ecosystem: it powers the chat assistants of
the [showcase website](https://capturemoment.vercel.app/) and of the
[documentation](https://capture-moment.github.io/docs/).

The project maintains the **knowledge base** (general + technical content,
embedded into `index.json`), and exposes the **chat API** deployed on Vercel.

> Companion repos:
> [Capture-Moment/docs](https://github.com/Capture-Moment/docs) — MkDocs guides,
> [Capture-Moment/CaptureMoment](https://github.com/Capture-Moment/CaptureMoment) — the application.

## 🧠 How it works

The chat follows a classic **RAG** (Retrieval-Augmented Generation) pipeline:

```
knowledge sources          build time (CI)                 runtime (Vercel)
─────────────────          ─────────────────────────       ───────────────────
dataset/information.md ─┐
                        ├─► chunking → embeddings ─► index.json ─► /api/chat
docs repo (*.md) ───────┘    (tagged per source)    (committed)     retrieval + LLM
```

Every knowledge chunk is **tagged with its source**:

- `general` — commercial / presentation content (`dataset/information.md`),
  answering "what is CaptureMoment", pricing, contact…
- `docs` — technical content, fetched **directly from the docs repository at
  build time**, answering build, architecture and testing questions.

The chat API routes the question to the right source based on retrieval scores
(technique → `docs`, general → `general`), so users always get answers anchored
in the relevant content — no manual curation, no duplicated files.

## 📁 Repository structure

```
.
├── api/                      # Vercel serverless functions (chat endpoint)
├── rag/                      # ingestion, embedding and retrieval logic
├── dataset/
│   └── information.md        # general/commercial knowledge (hand-maintained)
├── index.json                # generated embeddings index — built by CI, never by hand
├── requirements.txt          # Python dependencies
├── tests/                    # pytest suite
└── .github/workflows/
    └── ci-cd-llm.yml         # CI (tests) + CD (index rebuild on main)
```

## ⚙️ CI/CD

| Event | What happens |
|---|---|
| Push / PR on `develop` | **CI**: `pip install -r requirements.txt` + `pytest` |
| Push on `main` | **CI + CD**: tests, then clone the `docs` repo, rebuild `index.json`, commit it → Vercel deploys |
| Docs merge (repository_dispatch) | Same as above — triggered automatically by the `docs` repo CI |
| Manual | `workflow_dispatch` from the Actions tab |

> `index.json` is a **build artifact**: it is always regenerated by CI,
> never edited locally or committed by hand.

## 💻 Local development

```bash
pip install -r requirements.txt

# run the tests
pytest

# rebuild the index locally (dev only — CI produces the official one)
python -m rag.build_index --general dataset/information.md --docs-path <path> --output index.json

# query the retrieval module
python -m rag.retrieval
```

## 🔐 Security model

- The **LLM API key lives only in Vercel** (Environment Variables, server-side).
  It is never embedded in any static file or client script.
- The clients (`chat.js` on the website, `chat.js` on the docs) only know the
  **public API URL**.
- CI secrets (`CI_GH_TOKEN`) are used at build time only, to commit the
  regenerated `index.json`.

## 🚢 Deployment

- **Vercel** hosts the API (serverless functions) and serves `index.json` as a
  static asset. The production branch is `main` — merging to `develop` never
  touches production.
